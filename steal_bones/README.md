# Steal Bones

Реализация по ТЗ (`steal_bones_tz.md`) — сбор публичной активности на NFT/
мемкоин-площадках, проверка баланса кошельков, фильтр по порогу, БД с
дедупом, экспорт в Excel. Чёрная тема с "костяной" эстетикой.

## Запуск

```bash
pip install -r requirements.txt
cp .env.example .env        # заполните только те ключи, которые реально нужны —
                             # см. вкладку «Ключи API» в самом приложении
python3 main.py
```

Открыть `http://127.0.0.1:5000`.

## Отличия от исходного текста ТЗ — и почему

Код писался в среде **без сетевого доступа** (ни `pip install`, ни живые
запросы к Magic Eden/Etherscan/и т.д.). Это повлияло на два решения:

**1. Стек.** Исходный черновик называл FastAPI/httpx/SQLAlchemy/tenacity/
loguru/pydantic-settings. Эти пакеты нельзя было поставить в среде
разработки — но Flask/requests/pandas/openpyxl уже стояли предустановленными,
и именно поэтому весь код ниже реально запускался и проверялся построчно, а
не писался "вслепую". Сам ТЗ уже называл Flask допустимой альтернативой
(раздел 2). Архитектурно ничего не изменилось — тот же интерфейс адаптеров,
та же схема БД, та же логика rate-limit guard, — просто:
- FastAPI → **Flask**
- httpx → **requests**
- SQLAlchemy → **sqlite3** (stdlib), напрямую те же таблицы/SQL
- tenacity → свой `with_backoff()` (rate_limit/guard.py) — три строчки,
  делает то же самое
- loguru → стандартный `logging`
- pydantic-settings + python-dotenv → свой мини-загрузчик `.env` (тоже
  несколько строк, config.py)

Если хотите вернуться к исходному стеку — на вашей машине с интернетом
`pip install fastapi uvicorn httpx sqlalchemy tenacity loguru
pydantic-settings` встанет без проблем, а перенос несложный: интерфейсы
адаптеров (`MarketplaceAdapter`, `BalanceAdapter`) от Flask/SQLAlchemy не
зависят вообще, менять пришлось бы только `main.py` и `db/models.py`.

**2. Что реально проверено, а что — best-effort.** Без сети нельзя было
дёрнуть настоящие Magic Eden/OpenSea/Etherscan и посмотреть на живой ответ.
Поэтому:

| Слой | Статус |
|---|---|
| БД, дедуп/upsert, кэш баланса | ✅ Протестировано (`tests/`, реальные вставки/апдейты в sqlite) |
| Rate Limit Guard (квота, ротация ключей, backoff) | ✅ Протестировано, включая персистентность между "перезапусками" |
| Excel-экспорт | ✅ Протестировано (генерация + чтение обратно) |
| Flask-приложение целиком (все страницы, форма, job → results → export, сохранение ключей) | ✅ Протестировано через Flask test client, end-to-end, включая один найденный и исправленный баг (сохранение ключей в Settings сбрасывало путь к БД) |
| Парсинг ответов Magic Eden / OpenSea / Solana RPC / EVM RPC / mempool.space / TronGrid / Sui RPC | ✅ Логика парсинга протестирована на **замоканных** ответах (`tests/test_adapters.py`), но **форма самого ответа — предположение** по документации/памяти, не проверено вживую |
| Tensor, LooksRare | ⚠️ Авторизация верна, сам запрос/эндпоинт помечен как "сверить по документации после получения доступа" — оба сервиса выдают API только по заявке, схему заранее было неоткуда взять |
| Rarible, Birdeye | ⚠️ Best-effort по документированной структуре, не проверено вживую |
| Blur | ❌ Официального API нет — адаптер честно объясняет это и указывает на агрегаторы (Bitquery и т.п.) вместо того, чтобы бить в несуществующий эндпоинт |
| DexScreener | ℹ️ Реализовано то, что он реально умеет (проверка токена/пары) — он **не отдаёт** адреса кошельков по сделкам, для этого в пайплайне используется Birdeye |

**Перед боевым запуском:** заведите нужные ключи (вкладка «Ключи API» в
приложении), запустите один сбор на маленьком лимите и проверьте вкладку
Results — если поля пустые там, где не должны быть, значит у площадки
изменилась форма ответа и `_parse_*`/`ACTIVITY_QUERY` в соответствующем
файле адаптера нужно поправить под реальный JSON.

## Исправления по итогам реального тестирования (03.08.2026)

По логам из реального прогона на Windows нашлись и исправлены:

1. **Фильтр продаж Magic Eden угадывался неверно.** Реальные данные показали:
   запись с `type: 'bid'` содержит `buyer`, но не содержит `seller` вовсе —
   это заявка на покупку, а не сама продажа. Вместо угадывания точной строки
   типа события теперь продажа определяется по факту: есть И `buyer`, И
   `seller` одновременно.
2. **Мало/ноль продаж в первых 500 записях.** У активно торгуемых через
   пул-механику (`source: mmm`) коллекций прямые продажи могут не попадаться
   даже в 500 последних событий. Добавлена пагинация вглубь истории (до 60
   страниц) с остановкой, когда набралось нужное количество уникальных
   кошельков.
3. **Баг с сетью:** баланс проверялся в сети, которую пользователь выбрал в
   форме, а не в той, к которой реально относится собранная активность —
   Solana-адреса с Magic Eden уходили на проверку в Ethereum/Bitcoin RPC и
   гарантированно проваливались. Теперь сеть для проверки баланса берётся из
   самой активности (`ActivityRecord.network`); Dashboard дополнительно
   блокирует выбор сети для одно-сетевых площадок (Magic Eden/Tensor →
   Solana, Blur/LooksRare → Ethereum), чтобы не допустить рассинхрона.
4. **Захардкоженное "10 кошельков".** Глубина поиска (сколько уникальных
   кошельков минимум набрать перед остановкой пагинации) была зашита
   константой = 20 внутри адаптера. Вынесено в поле Dashboard «Сколько
   кошельков минимум искать» и пробрасывается через весь пайплайн.
5. **Живая валидация коллекции.** Добавлена лёгкая проверка введённого
   символа коллекции для Magic Eden (`/api/check-collection`) — сразу видно,
   существует ли коллекция с таким символом, до запуска сбора. Полноценный
   "список топ-коллекций" для автоподбора не реализован — под него нет
   подтверждённого вживую эндпоинта ни у одной из 6 площадок; при желании
   можно донастроить так же итеративно, как чинили activities-эндпоинт.

## Второй раунд исправлений (по логам и скриншоту от 03.08.2026)

1. **Реальный баг: `disabled`-select не отправляется с формой.** Авто-блокировка
   сети под площадку (см. выше) была сделана через `networkEl.disabled = true`
   — но браузер вообще не отправляет disabled-поля при сабмите формы. Из-за
   этого сервер получал сеть по умолчанию (solana) для ЛЮБОЙ площадки с
   фиксированной сетью, включая Ethereum-площадки (Blur/LooksRare). Внешне
   выглядело так, будто "выбор сети не работает" — он и правда не работал.
   Исправлено: поле больше не блокируется, только предзаполняется нужным
   значением и остаётся кликабельным (форма теперь всегда отправляет то, что
   реально выбрано).
2. **"Всегда мало кошельков" (8–11).** При разборе оказалось, что это
   ожидаемое поведение при настройках по умолчанию (target_wallets=20, порог
   1 SOL: из ~20 найденных примерно половина проходит порог) — не баг, а
   следствие невысокого лимита по умолчанию. Добавлено явное логирование
   полученного из формы `target_wallets` в консоль main.py — если при
   увеличении этого поля число кошельков не растёт, это будет видно по логу
   сразу, и понадобится новый раунд диагностики (как с activities).
3. **Топ-коллекции (экспериментально).** Добавлена кнопка на Dashboard
   «Показать топ коллекций» — дёргает `/collections` у Magic Eden. ЧЕСТНО:
   этот эндпоинт, в отличие от `/activities` и `/stats`, не подтверждён
   вживую — это осознанная догадка по общей форме REST API площадки. Если
   список окажется пустым/неверным — это ожидаемо для эксперимента; пришлите
   лог консоли (там та же подробная диагностика, что помогла с activities) —
   поправим по факту.

## Третий раунд исправлений (по скриншоту и жалобам от 03.08.2026)

1. **"0 проверено из 4 найденных" — оказался кэш баланса, не баг.**
   Кошельки, которые уже проверялись в предыдущих тестовых запусках той же
   коллекции за последние 24ч (раздел 3.5 ТЗ), молча пропускались — со
   стороны выглядело как поломка. Теперь это явно показывается в сводке
   ("N кошельков пропущено — недавно проверялись") и на Dashboard появился
   чекбокс **«Игнорировать кэш баланса»** — форсирует полную перепроверку.
2. **"Каша" на Результатах после повторных запросов.** Страница показывала
   всю накопленную базу вперемешку, без разделения на "то, что нашёл этот
   запуск" и "всё остальное". Теперь после запуска сбора автоматически
   применяется фильтр по коллекции/токену (`?collection=...`), результаты
   показывают только то, что нашёл именно этот запуск, плюс ссылка
   «показать всю базу» и отдельное поле фильтра по коллекции в тулбаре.
3. **Топ-коллекции — заменены на статический список.** По прямой просьбе
   пользователя: вместо запроса к неподтверждённому эндпоинту Magic Eden —
   захардкоженный список из 8 известных Solana NFT-коллекций
   (mad_lads, degods, y00ts, okay_bears, claynosaurz,
   famous_fox_federation, degenerate_ape_academy, solana_monkey_business).
   ЧЕСТНО: точность символов по памяти, не 100% гарантирована — но клик по
   варианту сразу запускает уже проверенную живую валидацию
   (`/api/check-collection`), так что неверный символ будет виден по ✗ ещё
   до запуска сбора. Динамический вариант (`get_top_collections`) оставлен
   в коде адаптера неиспользуемым — задел на будущее, если понадобится.
4. **"Результаты несерьёзные".** В основном это следствие пунктов 1–2:
   таблица показывала старые записи вперемешку с новыми, из-за чего
   впечатление размывалось. С фильтром по коллекции и явным кэш-репортингом
   должно быть яснее, что именно нашёл конкретный запуск. Если после этого
   балансы всё ещё кажутся мелкими — это вопрос настройки порога
   (`min_balance`), а не бага: с порогом 1 SOL естественно попадётся много
   некрупных кошельков, для отбора действительно крупных стоит поднимать
   порог существенно выше (десятки/сотни SOL).

## Четвёртый раунд — архитектурные изменения (по логам и скриншотам 04.08.2026)

Это уже не мелкие правки, а переработка ядра пайплайна по итогам реального
использования:

1. **`target_wallets` теперь честно означает "кошельков с нужным балансом",
   а не "найденных вообще".** Раньше поиск останавливался, как только
   находил N кошельков в активности, — балансы почти всех могли не пройти
   порог, и в итоге "цель 20, порог 500 SOL" отдавала 1 сохранённый. Теперь
   для Magic Eden (единственная площадка с постраничным поиском) цикл живёт
   в `pipeline.py`: страница активности → сразу проверяем баланс новых
   кошельков → считаем, сколько прошло порог → если мало — листаем
   следующую страницу, и так до `target_wallets` прошедших порог, конца
   истории или потолка страниц/квоты.
2. **Обнаружен и учтён реальный потолок API Magic Eden.** По логам —
   стабильный HTTP 400 на offset≈15500 на нескольких разных коллекциях.
   `MAX_OFFSET = 15000` в `magic_eden.py` отражает это эмпирически; при
   достижении потолка пользователю прямо говорится, что дальше листать
   некуда, а не молча возвращается недостаточно данных.
3. **Сохраняются ВСЕ проверенные кошельки, не только прошедшие порог.**
   Раньше непрошедшие кошельки не попадали в БД — из-за этого кэш баланса
   (24ч) на них не работал (перепроверялись впустую каждый раз), и не было
   способа посмотреть "что вообще было найдено". Теперь порог применяется
   только при показе/экспорте (`min_balance` в фильтре), а не при записи.
4. **Таблица Результатов теперь сортируется** по клику на заголовок колонки
   (адрес/сеть/баланс/площадка/дата).
5. **Прогресс вместо консоли.** `/run-job` больше не блокирует браузер на
   минуты — job уходит в фоновый поток (`threading.Thread`), сразу
   показывается страница `/job-progress` с анимированным индикатором
   (пульсирующий череп), прогресс-баром и живыми счётчиками (страница /
   найдено / проверено / прошло порог), опрашивающая `/api/job-status`
   каждые ~800мс. Упрощение (см. `progress.py`): состояние — один глобальный
   объект, инструмент однопользовательский, двух одновременных сборов не
   потянет — и не должен.
6. **Живая проверка коллекции расширена на OpenSea** (`check_collection_exists`
   в `opensea.py`) — 404 на "robinhood_chimps" был, скорее всего, просто
   неверным слагом, а не поломкой ключа/адаптера; теперь это видно сразу на
   Dashboard до запуска сбора.
7. **Статический список популярных коллекций расширен на OpenSea**
   (boredapeyachtclub, azuki, doodles-official, pudgypenguins, clonex,
   mutant-ape-yacht-club). ЧЕСТНО: для Tensor/Rarible/LooksRare такой список
   не добавлен — Rarible использует контрактные адреса (риск случайно
   подсунуть неверный хэш выше, чем у текстового слага), а Tensor/LooksRare
   требуют ключ по заявке, так что смысла тестировать список без него мало.
8. **Про "проверь все API-ключи":** я не могу лично протестировать все ключи
   вживую — у меня нет аккаунтов/ключей ни на одной из площадок, и в среде,
   где пишется код, нет сетевого доступа. Что я могу и сделал —
   перепроверил код каждого адаптера на предмет очевидных ошибок (URL,
   заголовки, обработка ошибок) и добавил живую валидацию коллекции там,
   где это осмысленно (Magic Eden, OpenSea). Для Tensor/Rarible/LooksRare/
   Birdeye реальная проверка возможна только с вашими настоящими ключами —
   если какой-то из них выдаст ошибку, пришлите лог так же, как с Magic
   Eden, разберём по факту.

## Пятый раунд — реальные баги из логов и скриншотов (05.08.2026)

1. **Несколько ключей Helius через запятую ломали всё (401 на каждый запрос).**
   Пользователь ввёл 3 ключа Helius через запятую в Settings (по аналогии с
   подсказкой у Etherscan-поля) — а `helius_key` был одиночной строкой, весь
   текст с запятыми уходил в URL как один "ключ". Теперь `helius_keys` —
   список с настоящей ротацией через `KeyRotator`, как у Etherscan; если все
   ключи в пуле исчерпаны — тихий откат на бесплатный публичный RPC, а не
   падение.
2. **Главный баг: OpenSea реально запускался с сетью Solana.** Раньше
   мультичейн-площадки (OpenSea/Rarible/Birdeye) могли выбрать любую из 10
   сетей — ничего не мешало собрать Ethereum-коллекцию (BAYC) с сетью Solana
   в форме, и все проверки баланса гарантированно проваливались. Теперь для
   каждой площадки — точный список того, что она реально поддерживает
   (`PLATFORM_NETWORKS` в `main.py`), выпадающий список Сети на Dashboard
   строится только из него, и **дополнительно** сервер сам поправляет
   несовместимую пару, если её всё же прислали (защита в глубину — вдруг JS
   не выполнился или кто-то шлёт запрос напрямую).
3. **Список коллекций для подбора теперь зависит от связки площадка+сеть**,
   не только от площадки. Уверенно заполнен только для Magic
   Eden+Solana и OpenSea+Ethereum — для остальных комбинаций коробка
   честно не показывается, вместо того чтобы гадать.
4. **Про "баланс всегда в SOL" (п.1 вопроса)** — конвертации валют нигде
   нет и не было: баланс каждой сети показывается в её нативной единице
   (ETH для Ethereum, TRX для Tron и т.д.), и порог `min_balance`,
   который вы вводите, читается буквально в единицах ВЫБРАННОЙ сети —
   набрали "500" на Ethereum, это значит "500 ETH", а не доллары и не
   SOL. Юнит рядом с полем порога должен был обновляться при смене сети и
   раньше — но теперь, когда сети ограничены под площадку, спутать её
   с чужой стало физически сложнее.

## Шестой раунд — по логам и скриншотам пользователя (08.08.2026)

Пользователь прислал полный лог PowerShell (Magic Eden: solana_monkey_business,
mad_lads, degods, famous_fox_federation; OpenSea: boredapeyachtclub,
doodles-official) и 5 скриншотов Dashboard с шестью конкретными вопросами.
Разобрано по коду, не по догадке:

1. **"Баг или реально нет таких кошельков?" — ни то, ни другое в чистом
   виде.** `MAX_OFFSET = 15000` в `magic_eden.py` — это не квота, которая
   "обновится, если подождать", а эмпирически найденный потолок ГЛУБИНЫ
   ИСТОРИИ конкретного эндпоинта (`/collections/{slug}/activities`
   стабильно отвечает HTTP 400 на offset≈15500, см. round 4). Ждать и
   пробовать тот же offset ещё раз бессмысленно — это не rate-limit-подобное
   500/429. При этом в логе пользователя (07:52:11, mad_lads, target_wallets=1)
   поиск ДЕЙСТВИТЕЛЬНО нашёл кошелёк с балансом ≥ 500 SOL ("1 из 9 сохранённых
   прошли порог 500.0") — то есть механизм работает, просто порог высокий
   (500 SOL — это соизмеримо с few dozens тысяч долларов, ликвидный SOL на
   торговом кошельке редко бывает такой) и в рамках ОДНОЙ коллекции выборка
   некрупная (11-56 уникальных адресов на попытку). Правильный рычаг — не
   ожидание, а батч-режим (см. ниже): поле "Коллекция" на Dashboard теперь
   принимает список через запятую, target_wallets становится общей целью на
   весь список, обработка следующей коллекции начинается только если
   предыдущие не набрали нужное число. pipeline.py::run_job.
2. **"Какой баланс вообще проверяется?"** — только НАТИВНЫЙ баланс сети
   (`eth_getBalance` / `getBalance` RPC-методом): SOL на Solana, ETH на
   Ethereum и т.д. НЕ включены: NFT в самом кошельке, SPL/ERC-20-токены,
   застейканные/обёрнутые активы. Это не баг — так и было задумано (раздел
   3.3 ТЗ, "баланс" = нативная монета), но нигде явно не объяснялось
   пользователю. Теперь есть явная пометка у поля порога на Dashboard и
   расширенный docstring в `evm.py`/`solana.py`.
3. **"Кошельки как будто заново проверяются между коллекциями, но не нашёл
   ни одного".** Кэш (address, network) → 24ч НЕ зависит от коллекции —
   значит, ровно наоборот: повторно встреченный кошелёк ПРОПУСКАЕТСЯ, а не
   перепроверяется (см. `skipped_recent_check` в сводке). Отдельно нашлась
   вторая, ранее необъяснённая причина расхождения "уникальных" и
   "проверенных": как только на странице набирается нужное число ПРОШЕДШИХ
   порог кошельков, остаток уже найденных на этой же странице просто не
   проверяется (нет смысла тратить квоту) — но это никак не показывалось.
   Теперь `JobResult.stopped_early_at_target` и текст в summary_text()
   делают это explicit.
4-6. **OpenSea "собирает кошельки, но не проверяет балансы", консоль
   выглядит зависшей, итог всегда 0.** Все три — следствие ОДНОЙ причины,
   видной в самом логе: ~60 подряд `SSLError` ("EOF occurred in violation of
   protocol") при обращении к `eth.llamarpc.com` — публичный RPC для
   Ethereum. `EvmBalanceAdapter.get_balance()` делал РОВНО одну попытку без
   единого повтора и без резервного узла — при сбое конкретно этого хоста
   КАЖДЫЙ EVM-адрес молча проваливался (`except BalanceCheckError: return` в
   `pipeline.py`), а `progress.update()` для счётчика "проверено" вызывался
   только при УСПЕХЕ — отсюда и "статичная консоль" (менялся только таймер,
   см. Image 4). Исправлено:
   - `evm.py`: до 3 публичных RPC-узлов на сеть по очереди + `with_backoff`
     (rate_limit/guard.py — уже был реализован и протестирован, но нигде не
     подключён) на каждом. `solana.py` — та же обёртка, без доп. узла (нет
     проверенного вживую резерва).
   - `magic_eden.py`: тот же `with_backoff` перед тем, как трактовать сбой
     на offset>0 как "дошли до потолка истории" — иначе один временный сбой
     посреди пагинации мог преждевременно остановить весь поиск.
   - `pipeline.py`: `JobResult.rpc_failures` считает технические сбои ОТДЕЛЬНО
     от `wallets_qualifying`/`balances_checked` — если сбоев много, в
     warnings отдельная явная строка с текстом последней ошибки, а не общая
     "площадка не поддерживает глубокий поиск" (которая раньше маскировала
     реальную причину).
   - `progress.py` / `job_progress.html`: новые счётчики `balances_attempted`
     (успех+неуспех) и `rpc_failures`, обновляются на КАЖДУЮ попытку — на
     Панели прогресса появилась 5-я плитка "Ошибок RPC", которая тикает в
     реальном времени, даже если ни одна проверка не проходит успешно.
   - **Бонус, тем же корнем:** `opensea.py` был single-shot (максимум 50
     событий за весь job, независимо от target_wallets). По официальному
     changelog OpenSea (`docs.opensea.io/changelog/cursor-pagination`)
     `/events` поддерживает курсорную пагинацию с 2022 года — адаптер её не
     использовал. Теперь у OpenSea есть `fetch_activity_page` (курсор
     хранится на экземпляре адаптера между вызовами) и `supports_deep_search
     = True`, так что он листает историю вглубь так же, как Magic Eden —
     раньше физически не мог набрать больше 50 событий на коллекцию.

## Седьмой раунд — по итогам живого тестирования шестого раунда (08.08.2026)

Пользователь прогнал батч по 4 коллекциям на Magic Eden и по 3 на OpenSea,
прислал два скриншота с результатами и четыре запроса на доработку.

**Разбор скриншота Magic Eden ("из 192 записей активности — только 98
кошельков, не теряем ли часть?")**: дедупликация сама по себе — не баг
(активные трейдеры естественно повторяются между сделками). РЕАЛЬНАЯ
находка при разборе `_parse_items`: код требовал ОДНОВРЕМЕННО buyer И
seller — то есть считал только ЗАВЕРШЁННЫЕ продажи, полностью отбрасывая
участников, которые только выставили NFT на продажу (нет buyer) или
сделали ставку (нет seller), хотя ставка на Magic Eden обычно эскроуится
(под неё реально зарезервированы средства — валидный сигнал
платёжеспособности). Исправлено: теперь учитываются buyer+seller
(role="buyer"/"seller", как раньше) И одиночные события (role="bidder"
для ставки без продавца, role="lister" для листинга/делистинга без
покупателя) — это отвечает на вопрос "не теряем ли кошельки" и одновременно
даёт больше кандидатов со страницы, что помогает и с MAX_OFFSET (раунд 6).

**Скриншот OpenSea** — рабочее подтверждение раунда 6: батч по коллекциям
("Коллекций обработано: 2 из 3"), явное объяснение `stopped_early_at_target`
("не все проверены — цель уже была достигнута раньше"), и вместо прежних
~60 подряд SSLError — ровно 1 изолированный сбой из 102 попыток, явно
подписанный отдельным предупреждением с точным текстом ошибки. Ретрай +
резервные RPC-узлы из раунда 6 сработали как задумано.

Дальше — четыре доработки по итогам обсуждения:

1. **Пауза с таймером на HTTP 429, без сброса прогресса.** Новое исключение
   `RateLimited` (rate_limit/guard.py) — отдельно от `AdapterError`
   (сбой запроса) и `BalanceCheckError`/обрыва соединения. Это
   ПРИНЦИПИАЛЬНО не то же самое, что `MAX_OFFSET` (структурный потолок,
   ждать бессмысленно) — 429 это "слишком часто, подожди", и здесь
   ожидание реально помогает. Проверены документации обеих площадок:
   у OpenSea 429 **гарантированно** сопровождается заголовком `Retry-After`
   (используется как точное время ожидания, с запасом ×1.25 — часы клиента
   и сервера могут немного расходиться); у Magic Eden такой гарантии в
   открытой документации не нашлось — тогда используется собственная оценка
   `DEFAULT_RATE_LIMIT_WAIT_SEC = 90` (обоснование в коде: у Magic Eden
   документирован QPM-лимит вида "в минуту", такие окна обычно закрываются
   в пределах той же минуты — 90с = 60с + 50% запас, а не выдуманное точное
   число). `pipeline.py::_wait_out_rate_limit` ставит job в статус "пауза"
   (`progress.pause`), ждёт и возвращает в "выполняется" — offset/курсор
   при этом НЕ сбрасывается, все адаптеры (magic_eden.py, opensea.py,
   evm.py, solana.py) гарантируют, что `RateLimited` поднимается ДО того,
   как продвигается offset/курсор. Если для сервиса настроен пул из
   нескольких ключей (сейчас — только Solana/Helius, `KeyRotator`) — сначала
   тихо пробуем следующий БЕЗ ожидания (`mark_rate_limited`/`has_other_key`),
   таймер показывается только когда ключей больше нет. На странице
   /job-progress — отдельный явный блок "Пауза — лимит запросов площадки" с
   живым обратным отсчётом и пояснением, что ничего нажимать не нужно.
2. **extra_assets — "хотя бы часть активов" сверх нативного баланса.**
   Приоритет — Solana, бесплатно, без ключа и без привязки карты (именно
   так и запрошено). `SolanaBalanceAdapter.get_token_holdings` —
   `getTokenAccountsByOwner` одним RPC-вызовом отдаёт ВСЕ SPL-токен-аккаунты
   адреса, без сторонних индексаторов; известные стейблкоины (USDC/USDT)
   показываются по имени и сумме, остальные — счётчиком без резолва имени.
   Для EVM — `EvmBalanceAdapter.get_known_token_balances`: прямой `eth_call`
   к `balanceOf(address)` на заранее известных, сверенных по Etherscan
   адресах контрактов (сейчас — USDC/USDT на Ethereum mainnet) — тоже БЕЗ
   стороннего индексатора и без ключа, тем же публичным RPC, что и для
   нативного баланса (проверено: Etherscan API исторически даёт бесплатный
   тариф без привязки карты, но раз можно обойтись прямым RPC-вызовом —
   зачем ещё одна зависимость). Ограничение метода: работает только для
   токенов из заранее заданного списка (в отличие от Solana, на EVM нет
   способа "перечислить все токены адреса" одним RPC-вызовом) — список
   расширяемый, см. `KNOWN_ERC20_TOKENS` в evm.py. Сбой получения доп.
   активов НЕ роняет основную проверку баланса (это дополнительные данные).
3. **Учёт держателей коллекции, не только ленты активности.** По итогам
   разбора п.1 обсуждения (не теряем ли кошельки из-за глубины истории):
   у OpenSea официально подтверждён (opensea-js, метод `getNFTsByCollection`)
   способ получить ТЕКУЩИХ владельцев NFT коллекции — не ограничен глубиной
   истории активности, только размером самой коллекции. Для Magic Eden
   аналог целенаправленно проверялся и НЕ подтверждён (единственная
   похожая зацепка оказалась в архивной, с 2023 года, неофициальной
   документации по другому, устаревшему API-домену — см. итоги проверки
   ниже) — поэтому вторая фаза реализована только для OpenSea.
   `fetch_holders_page` (opensea.py) листает `/collection/{slug}/nfts` по
   курсору; `pipeline.py` включает эту фазу ПОСЛЕ того, как обычная лента
   активности исчерпана, если цель по кошелькам ещё не достигнута — дописывая
   в те же `seen_wallets`, так что дедуп с уже найденными по активности
   работает автоматически. ЧЕСТНО: путь эндпоинта и имя поля "owner" — по
   описанию официального SDK и стороннего API-wrapper'а, не проверены
   вживую (нет сетевого доступа в среде разработки) — если реальный ответ
   будет отличаться по форме, поправить нужно только `_parse_holders`.
4. **Учёт "застрявших" в кэше кошельков.** Раньше пропуск по кэшу (24ч,
   раздел 3.5) нигде не фиксировался — кошелёк просто молча оставался со
   старой записью баланса. Теперь `times_skipped`/`last_skipped_at` —
   новые колонки в БД (миграция `ALTER TABLE` — не ломает уже существующие
   файлы БД пользователей, см. db/models.py), инкрементируются при каждом
   пропуске (`db/crud.py::record_skip`). На `/results` — переключатель
   "Пропущенные (в кэше)" с теми же фильтрами сети/коллекции, независимо от
   порога баланса, и своим экспортом в Excel.

**Что проверено и не подтверждено при разборе п.1 (для честности)**: искал
у Magic Eden эндпоинт "все текущие держатели коллекции" как альтернативу
ленте активности. Единственная похожая находка — сторонний репозиторий с
примером ответа, содержащим поле `owner`, — при полной проверке оказалась
архивной (владелец закрыл репозиторий в 2023 году) документацией по
СТАРОМУ RPC-style API (`api-mainnet.magiceden.io/rpc/*`), не тому REST API
(`api-mainnet.magiceden.dev/v2/*`), которым пользуется этот инструмент.
Даже в том архиве ближайший аналог — только "выставленные на продажу"
(тот же класс ограничения, что и активность) либо "NFT одного конкретного
кошелька" (не то направление). Вывод: для Magic Eden сейчас единственный
подтверждённый рычаг — батч по нескольким коллекциям (раунд 6).

Новые тесты (17 в pipeline + обновлённые в adapters): пауза на 429 с
продолжением с того же offset и без него (собственная оценка с запасом),
фаза держателей включается/не включается в зависимости от того, хватило ли
обычной ленты, доп. активы сохраняются и не роняют проверку при сбое,
пропуски по кэшу считаются и доступны отдельным фильтром. Плюс живой
end-to-end прогон через реальный Flask-клиент, включая паузу по 429.

## Восьмой раунд — по итогам живого батча на 5 коллекциях (09.08.2026)

**1. Находка и откат: бид-боты.** Батч на 5 коллекциях Magic Eden дал 77616
записей активности на 220 уникальных кошельков (~350:1 — до седьмого
раунда было ~1.6-2:1) и итоговый процент прохождения порога 1 из 169
(0.6%). Совпадает по времени ровно с добавлением `role="bidder"` в седьмом
раунде. Диагноз (по совокупности признаков, не проверено вживую — сетевого
доступа нет): ставки на Solana дёшевы (доли цента за транзакцию), это
делает выгодным для ботов держать floor непрерывным потоком
bid→cancel→re-bid — задокументированное в NFT-пространстве поведение,
особенно на Solana именно из-за низкой цены газа. Такие боты генерируют
подавляющую часть "активности" малым числом адресов, съедая бюджет
MAX_OFFSET на шум вместо покрытия большего реального периода торгов, и
сами почти никогда не проходят порог баланса (операционные кошельки).
Откат: `role="bidder"` (одиночный buyer без seller) больше не учитывается;
`role="lister"` (одиночный seller) — оставлен, так как у листинга/
делистинга нет той же экономики непрерывного обновления и он не давал
сопоставимого выброса в логах пользователя.

**2. UX: страница "Идёт сбор" была недостижима после ухода с неё.**
Два независимых исправления:
- `/job-progress` теперь виден на ЛЮБОЙ странице как лёгкий индикатор в
  шапке (виден только пока job реально running/paused, опрос раз в 3с,
  ведёт обратно на страницу прогресса) — не нужно помнить URL или искать
  вкладку.
- Сам маршрут `/job-progress` при статусе "idle" (сбор вообще не
  запускался) раньше молча показывал вечный пустой прогресс-бар на 0% —
  теперь редиректит на Панель с понятным сообщением. При статусе done/error
  страница по-прежнему открывается нормально и показывает финальную
  сводку — то есть вернуться к результатам ЗАВЕРШЁННОГО сбора (не только
  текущего) тоже можно.

**3. UX: слишком много поясняющего текста на Панели.** Длинные абзацы под
каждым полем заменены на одно короткое предложение с сутью + сворачиваемый
`<details>`/`<summary>` ("Подробнее ▸") для важных, но не всегда нужных
нюансов — сама информация не потеряна, просто не загромождает страницу по
умолчанию. Без JS, нативный HTML.

**4. Экспорт всей базы одной кнопкой.** Возможность технически уже была
(незаполненные фильтры = SELECT без WHERE), но не было явной, гарантированно
безфильтровой кнопки — при просмотре отфильтрованной выборки кнопка
экспорта раньше экспортировала именно её, а не всю базу. Добавлена вторая,
отдельная кнопка "Скачать всю базу (Excel)" на /results, которая ВСЕГДА
идёт без фильтров (все площадки, все сети, прошедшие порог, непрошедшие и
пропущенные по кэшу вместе), независимо от того, что выбрано в фильтрах
над таблицей.

## Осознанные упрощения / что не реализовано

- **Etherscan-ротация ключей.** `KeyRotator` и `ETHERSCAN_API_KEYS`
  полностью реализованы и протестированы как компонент, но ни один
  текущий адаптер их не вызывает — баланс EVM-сетей идёт через
  бесплатный RPC напрямую, а "доп. данные сверх баланса" (история
  транзакций и т.п. через сам Etherscan) в этой версии не реализованы,
  только сам баланс. Это задел на будущее расширение, а не мёртвый код
  без причины.
- ~~Дедуп ниже порога~~ и ~~job выполняется синхронно~~ — оба пункта,
  раньше перечисленные здесь как упрощения, исправлены в четвёртом раунде
  выше (сохраняются все проверенные кошельки; job теперь в фоновом потоке
  с live-прогрессом).
- **Прогресс — не персистентный между перезапусками main.py.**
  `progress.py` хранит состояние текущего job в памяти процесса; если
  перезапустить сервер посреди сбора, страница `/job-progress` покажет
  "idle", а сам фоновый поток (демон) прервётся вместе с процессом. Для
  локального однопользовательского инструмента это осознанный компромисс
  простоты, не редизайн под перезапускоустойчивость.
